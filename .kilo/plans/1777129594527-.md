# New Session Prompt Plan

Use the prompt below in a fresh coding session.

---

You are working on Karna, a Cloudflare Pages + Hono + D1 personal AI assistant. Read `context.md` first, then inspect the relevant files before editing. The user is non-technical but creative, so prioritize visible UX improvements, reliability, and clear behavior over abstract infrastructure work.

## Goal

Implement the first product-improvement bundle:

- 1. Action Center
- 2. Pending Actions Inbox
- 3. Better Notifications
- 4. Reminder Snooze and Reschedule Buttons
- 5. Better Dashboard Home Screen
- 6. Memory Review Page
- 10. Memory Suggestions
- 11. Document Library
- 13. Document Summaries
- 16. Morning Briefing
- 19. Email Digest
- 21. Weekly Review
- 32. Message Actions

Important user context: Outlook support matters. The user does not have org admin permission for Outlook API access, so Outlook must be handled through the existing Browser Use Cloud + Secret Vault flow. Any email-related feature in this build must include both Gmail and Outlook paths. Gmail can use Google OAuth APIs. Outlook must use browser automation with saved vault credentials.

## Product Direction

Make Karna feel more like a daily personal command center, not only a chat window. The first release should be practical and shippable: visible dashboards, useful actions, and simple retry/approval flows. Avoid overbuilding advanced AI search unless required.

## Existing Architecture To Use

- Frontend SPA is embedded in `src/frontend.ts` with CSS in `public/static/karna.css`.
- Main routes are in `src/routes/*`.
- Agent tools and prompts are mainly in `src/services/agent.ts`.
- Memory service is in `src/services/memory.ts`.
- Gmail service is in `src/services/gmail.ts`.
- Browser Use Cloud service is in `src/services/browser.ts`.
- Secret Vault routes are in `src/routes/settings.ts` under `/api/settings/site-vault`.
- Notifications are currently in `src/routes/chat.ts` under `/api/chat/notifications*`.
- Uploaded files are in `uploaded_files`, with R2 support and `extracted_text`.
- Proactive routes are in `src/routes/proactive.ts`.
- Cron worker calls proactive endpoints from `cron-worker/worker.js`.

## Implementation Strategy

Do this in phases. Prefer one coherent build with migrations, routes, frontend UI, and agent prompt/tool updates. Keep changes compatible with existing user data.

---

# Phase 1: Data Model And Backend Foundations

Add D1 migrations for the minimum new structures needed.

Suggested tables/columns:

1. `action_items`
   - Tracks pending actions and inbox items.
   - Fields: `id`, `user_id`, `type`, `title`, `body`, `status`, `priority`, `source`, `source_id`, `action_payload`, `created_at`, `updated_at`, `due_at`, `completed_at`.
   - Status examples: `pending`, `needs_approval`, `running`, `completed`, `failed`, `cancelled`.
   - Types: `pending_google`, `pending_email`, `browser_task`, `reminder`, `document_summary`, `memory_suggestion`, `email_digest`, `weekly_review`, `manual`.

2. `memory_suggestions`
   - Stores proposed memories before they are accepted.
   - Fields: `id`, `user_id`, `type`, `title`, `content`, `importance`, `status`, `source_message_id`, `created_at`, `decided_at`.
   - Status: `pending`, `accepted`, `rejected`.

3. `document_library`
   - Indexes uploaded/connected documents for a visible library.
   - Fields: `id`, `user_id`, `file_id`, `drive_file_id`, `source`, `name`, `mime_type`, `size`, `summary`, `key_points`, `action_items_json`, `status`, `created_at`, `updated_at`.
   - Source: `upload`, `drive`.
   - Status: `uploaded`, `parsed`, `summarized`, `failed`.

4. Optional: extend `notifications`
   - Add optional fields if absent: `priority`, `status`, `due_at`, `action_payload`.
   - If safer, keep existing `notifications` untouched and derive richer notifications from `action_items`.

5. Optional: extend `briefing_preferences`
   - Add `morning_enabled`, `morning_time`, `email_digest_enabled`, `weekly_review_enabled`, `weekly_review_day`, `weekly_review_time`.
   - If the existing preferences table already supports these, use that instead.

Backend routes to add:

- `GET /api/action-center` — returns overview counts and grouped items for dashboard.
- `GET /api/action-center/pending` — pending actions inbox.
- `POST /api/action-center/:id/complete`
- `POST /api/action-center/:id/cancel`
- `POST /api/action-center/:id/retry`
- `POST /api/action-center/:id/approve` — for future approval flows.
- `GET /api/documents` — document library.
- `POST /api/documents/:id/summarize`
- `DELETE /api/documents/:id`
- `GET /api/memory/review` or extend `/api/settings/memory` with tier/type filters.
- `POST /api/memory-suggestions/:id/accept`
- `POST /api/memory-suggestions/:id/reject`
- Reminder actions: `POST /api/chat/notifications/:id/done`, `POST /api/chat/notifications/:id/snooze`, `POST /api/chat/notifications/:id/reschedule` or equivalent under `/api/action-center`.

Use shared authentication logic where possible. Do not expose another user's data.

# Phase 2: Action Center, Pending Inbox, Better Home Dashboard

Create a new main dashboard/home experience in `src/frontend.ts`.

The home screen should show:

- Today's summary.
- Open reminders/tasks.
- Pending actions.
- Browser tasks still running.
- Failed actions needing retry.
- Recent document summaries.
- Memory suggestions waiting for approval.
- Email digest preview if available.
- Weekly review preview if available.
- Quick actions.

Action Center sections:

1. `Today`
   - reminders due today
   - calendar snapshot if existing APIs support it
   - important notifications

2. `Pending`
   - pending Google saves
   - pending email/drafts
   - browser tasks in progress
   - failed document summaries
   - failed scheduled tasks

3. `Needs Approval`
   - memory suggestions
   - email send approvals if implemented
   - browser/Outlook actions that need user confirmation

4. `Recent Activity`
   - created docs/sheets
   - document summaries
   - recent reminders completed

Keep the UI simple, mobile-friendly, and consistent with the existing Paper & Circuit design. Do not redesign the entire app unless necessary.

# Phase 3: Better Notifications And Reminder Controls

Improve notification cards in the UI and, where practical, Telegram reminder messages.

For reminder notifications, add actions:

- Done
- Snooze 10 minutes
- Snooze 1 hour
- Tomorrow 9 AM
- Change time
- Delete/cancel

Implementation behavior:

- `Done` marks notification read/completed and updates the underlying schedule state if linked.
- `Snooze` updates or creates the next reminder time.
- `Tomorrow` uses the user's timezone.
- `Change time` can open a small prompt in the frontend or route the user to chat with a prefilled instruction.

If Telegram inline buttons are added, ensure callback queries are supported. Otherwise keep Telegram changes minimal and implement web controls first.

# Phase 4: Memory Review And Memory Suggestions

Build a Memory Review UI in Settings or a dedicated Memory page.

It should show:

- Working memory vs long-term memory.
- Type filters: preference, fact, context, decision, task.
- Search/filter field.
- Edit memory.
- Delete/forget.
- Promote to active memory.
- Demote/archive.

Memory Suggestions:

- Change automatic memory extraction so durable facts/preferences can be proposed instead of silently stored when appropriate.
- Add a visible queue: “Karna suggests remembering...”
- User can Accept or Reject.
- Accepted suggestions become real memory using `MemoryService.store()`.
- Rejected suggestions should not be shown again.

Keep existing direct `store_memory` behavior working for explicit user commands like “remember this.”

# Phase 5: Document Library And Auto Summaries

Create a Document Library from uploaded files and optionally Drive-read files.

When a file is uploaded through `/api/chat/upload`:

- Insert/update a `document_library` row.
- If text is extracted immediately, mark it parsed.
- Provide a summarize action.

Document summary should extract:

- short summary
- key points
- dates
- people/organizations mentioned
- money amounts if present
- action items
- risks/unknowns

Implementation options:

- Use the configured LLM provider where available.
- If no LLM provider is available, store the document without summary and show “summary pending.”
- Avoid blocking uploads for long summaries; use a route action or background `waitUntil` where safe.

Frontend Document Library should show:

- file name
- source: upload or Drive
- status: uploaded/parsed/summarized/failed
- short summary
- buttons: Ask in chat, Summarize, Extract tasks, Delete

For now, “Ask in chat” can prefill a chat message referencing the file/document. Full RAG can wait for a later phase.

# Phase 6: Morning Briefing, Email Digest, Weekly Review

Add proactive summary features.

## Morning Briefing

Add route similar to existing evening briefing:

- `POST /api/proactive/cron/morning-briefing`

It should include:

- today's date and timezone
- today's calendar events
- reminders/tasks due today
- important notifications/pending actions
- Gmail unread/important snapshot
- Outlook snapshot via browser if configured and enabled
- weather/travel only if existing API support makes it easy; otherwise skip

Add user preferences:

- morning briefing enabled
- preferred time
- delivery channel: web notification and/or Telegram

Update cron worker to call the morning briefing endpoint every minute; the endpoint itself should check each user's preferred time.

## Email Digest With Gmail And Outlook

Email digest must support both:

1. Gmail path
   - Use existing Gmail API service.
   - Summarize unread/recent important email.

2. Outlook path
   - Use Browser Use Cloud, not Outlook API.
   - Must follow existing Secret Vault flow.
   - Check for vault entries like `Outlook`, `Microsoft`, `Office 365`, or user-configured site name.
   - If no vault credential exists, show a clear setup message: “No Outlook credentials saved in Secret Vault. Add them in Settings → Secret Vault.”
   - Browser task should be one complete workflow: open Outlook web, log in using vault credentials if prompted, inspect recent/unread inbox, return sender/subject/snippet/action-needed items. Do not split into multiple browser tasks.

The digest should label sources clearly:

```txt
Gmail
- ...

Outlook
- ...
```

Never invent Outlook email content. If browser returns no output, say Outlook returned no content.

## Weekly Review

Add route:

- `POST /api/proactive/cron/weekly-review`

It should summarize:

- completed tasks/reminders
- missed/overdue reminders
- open tasks
- important emails from Gmail and Outlook if available
- documents created/summarized
- pending actions
- upcoming week calendar highlights

Deliver via notification and Telegram if configured.

# Phase 7: Message Actions

Add quick action buttons to assistant messages in the chat UI.

Useful actions:

- Copy
- Save to Google Doc
- Email this
- Turn into task
- Remember this
- Create reminder
- Shorter
- More detailed

Implementation details:

- Start with frontend buttons on assistant messages.
- For actions that need tools, send a new chat message automatically, for example:
  - “Save your previous answer to a Google Doc.”
  - “Create a reminder from your previous answer.”
  - “Remember this: [selected message].”
- Keep it simple; do not build a complex action execution system in the first version.

Email-related message actions must support Gmail and Outlook:

- Gmail: can create Gmail draft with OAuth.
- Outlook: should create a pending browser action or send the user through Browser Use + Secret Vault. Prefer draft/compose rather than send without explicit approval.

# Browser Use / Outlook Requirements

Because Outlook access depends on browser automation, improve the browser feature while implementing email improvements.

Required changes:

1. Verify whether Browser Use Cloud supports reusing `sessionId` on task creation.
   - `src/services/browser.ts` currently stores session IDs but does not pass them due to a TODO.
   - Confirm correct request field from Browser Use docs/API or current SDK.
   - If verified, implement session reuse.
   - If not verified, update comments and UI honestly.

2. Add a dedicated Outlook browser workflow helper/prompt pattern.
   - It should always be one browser task.
   - It should use `vault_lookup` / Secret Vault credentials.
   - It should request structured output: sender, subject, date, snippet, action_needed, priority.

3. Add user-visible status for browser tasks.
   - In Action Center, show running/timed-out browser tasks.
   - Add retry/check-status actions.

4. Never hallucinate browser results.
   - Preserve existing rule: if Browser Use returns no output, report no output.

# Keep This Build Practical

Avoid trying to fully implement every advanced version of these ideas in one pass. The first version should be reliable and visible. Prefer:

- clear dashboard sections
- useful backend routes
- simple buttons
- graceful fallbacks
- honest status messages
- Outlook included wherever email is included
